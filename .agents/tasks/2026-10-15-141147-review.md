# Bulk Certificate Generation Workflow Implementation

This implementation adds end-to-end bulk certificate generation capability to the FastAPI backend. A client submits one POST request with multiple recipients, the API creates a job and queues background processing via Celery, the worker generates personalized PDF certificates for each valid recipient, tracks progress atomically, and provides download endpoints for successful certificates. Individual recipient failures are isolated from each other.

The approach separates async FastAPI (API layer with asyncpg) from synchronous Celery workers (direct ORM with psycopg2). Three API endpoints handle job creation, status retrieval, and certificate download. The Celery task processes recipients sequentially, applying runtime validation to catch edge cases, generating PDFs with ReportLab, and updating status using atomic SQL increments to prevent race conditions. Job finalization logic sets COMPLETED, COMPLETED_WITH_ERRORS, or FAILED based on success and failure counts.

**Watch for:** Path traversal protection uses Python path resolution to ensure certificate downloads stay within the storage boundary (confirmed). Counters are incremented atomically at the database level to prevent lost updates from concurrent operations (confirmed). The Celery task does not have dedicated unit tests — behavior is verified through integration tests that mock the task (likely gap). Runtime validation at processing time adds a second layer beyond API validation (confirmed).

## High-level view

The async/sync boundary is explicit and documented: FastAPI routes use async services with AsyncSession and asyncpg, while the Celery task uses synchronous ORM with Session and psycopg2. This avoids async/await complexity in Celery workers and prevents connection pool conflicts. The trade-off is some code duplication between service methods (which are async for the API) and task logic (which is sync), but the MVP keeps this manageable.

Recipient isolation works by wrapping each certificate's generation in a try/except block and continuing the loop on failure. Runtime validation applies the same Pydantic schema validation a second time during task execution to catch any edge cases that passed API validation or were corrupted in storage. Validation failures and PDF generation failures both mark the certificate as FAILED without stopping the loop.

Progress counters use atomic SQL UPDATE statements (`GenerationJob.completed_count = GenerationJob.completed_count + 1`) rather than read-modify-write in Python, eliminating the race condition where concurrent workers or rapid updates lose increments. Job finalization reads the latest counters within the same transaction and sets status based on `failed_count == 0` (COMPLETED), `0 < failed_count < total` (COMPLETED_WITH_ERRORS), or `failed_count == total_recipients` (FAILED).

The certificate download endpoint constructs file paths from the database's `file_path` column, resolves both the storage root and the file path to absolute paths, and verifies the file path is a descendant of the storage root using `Path.is_relative_to()`. This prevents `../` or absolute path attacks. If the check fails or the file doesn't exist, the endpoint returns 404 rather than exposing path information.

Test coverage includes integration tests for API contract (job creation, status retrieval, certificate listing), API error cases (404 for unknown IDs, 422 for validation errors, 404 for missing files), and workflow scenarios (one failure doesn't block others, all failures mark job FAILED). The Celery task itself has no dedicated unit tests. Integration tests mock the task's `.delay()` to prevent actual queueing and verify the task was called, but they don't run the task logic. Tests marked with `@pytest.mark.skip` claim to require Docker/separate database transactions, meaning some failure isolation scenarios are documented but not executed in CI.

File storage uses a two-level hierarchy: `base_path/<job_id>/<cert_id>.pdf`. The file manager ensures job directories exist before generation begins, and the PDF generator creates parent directories if missing. Storage failures (permission denied, disk full) propagate as exceptions caught by the task's per-recipient try/except, marking that certificate FAILED without stopping others.

API validation enforces 1-1000 recipients at the Pydantic schema level and rechecks the configured maximum in the route handler. Empty batches and oversized batches are rejected with 422 before reaching the database. Email format, date range (no future dates), and non-empty strings are validated by Pydantic field validators.

## Async/sync boundary and architecture decision

The Celery task creates a synchronous engine by replacing `postgresql+asyncpg://` with `postgresql+psycopg2://` in the connection string. The trade-off is that async service methods like `JobService.increment_completed()` cannot be called directly from the task. The task reimplements progress tracking using direct SQL UPDATE statements instead.

## Per-recipient failure isolation in the Celery task

The task commits after each certificate update (mark SUCCESS or FAILED, increment counter), so if the task crashes mid-loop, already-processed certificates remain in their final state and unprocessed certificates stay PENDING. This means a task retry will reprocess only PENDING certificates, but there's no idempotency guard: if a certificate was marked SUCCESS but the file was deleted before the crash, a retry will attempt to regenerate it and fail (the database record is already SUCCESS, so it won't be in the PENDING query).

Runtime validation applies the same `RecipientInput` Pydantic schema to data read from the database during task execution. This catches edge cases like empty strings that passed API validation but were corrupted in the database, or constraints that changed between submission and processing.

## Atomic counter updates and job finalization

The current implementation uses atomic SQL UPDATE (`UPDATE generation_jobs SET completed_count = completed_count + 1 WHERE id = ?`) at the database level, eliminating the read-modify-write race where concurrent operations lose increments.

After the last certificate is processed, the task refreshes the job object to read the latest counters, then sets final status (COMPLETED if `failed_count == 0`, COMPLETED_WITH_ERRORS if `0 < failed_count < total`, FAILED if `failed_count == total_recipients`) and commits. There is a narrow window where a client reading the job between the last counter increment commit and the finalization commit sees counters complete but status still PROCESSING.

## Path traversal protection in certificate download

The download endpoint constructs file paths from `cert.file_path` (a relative path like `<job_id>/<cert_id>.pdf`). Without validation, an attacker who can insert a malicious `file_path` like `../../etc/passwd` could read arbitrary files.

The endpoint resolves both the storage root and the file path to absolute paths and verifies the file path is a descendant of the storage root using `Path.is_relative_to()`. On failure, the endpoint returns 404 rather than exposing path details. This defense-in-depth layer catches bugs, database corruption, or future code changes that bypass path construction.

## Test coverage gap: Celery task

The Celery task `generate_certificates_for_job` has no dedicated unit test file. Integration tests mock `.delay()` to prevent queueing but don't exercise the task logic itself. Tests marked `@pytest.mark.skip` document expected behavior (one failure isolated, all failures mark job FAILED, validation errors caught at runtime) but don't run in CI. This is acceptable for MVP if manual Docker-based testing has verified the workflow, but automated regression testing of the task's failure isolation logic, atomic counter updates, and job finalization is missing.
